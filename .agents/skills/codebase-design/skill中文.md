代码库设计
设计深度模块：大量行为隐藏在小型接口之后，放置在干净的接缝处，通过该接口可测试。在设计和重构代码的任何地方，都应使用这套语言和原则。目标是为调用者提供杠杆效应，为维护者提供局部性，为所有人提供可测试性。

术语表
请严格使用这些术语——不要用"组件"、"服务"、"API"或"边界"替代。统一语言是关键。

模块（Module）——任何拥有接口和实现的东西。有意识地规模无关：可以是一个函数、类、包，甚至跨层级切片。避免使用：单元、组件、服务。

接口（Interface）——调用者正确使用模块所需知道的一切：类型签名，还包括不变量、顺序约束、错误模式、所需配置和性能特征。避免使用：API、签名（过于狭窄——它们仅指类型层面的表面）。

实现（Implementation）——模块内部的东西，它的代码主体。区别于适配器（Adapter）：一个东西可以是一个具有大量实现的小型适配器（如一个 Postgres 仓库），也可以是一个具有少量实现的大型适配器（如一个内存假实现）。当讨论重点是接缝时用"适配器"，否则用"实现"。

深度（Depth）——接口处的杠杆效应：调用者（或测试）每学习一个接口单位所能触发的行为量。当大量行为隐藏在小型接口之后时，模块是深度的；当接口几乎和实现一样复杂时，模块是浅层的。

接缝（Seam）（Michael Feathers）——一个可以在不修改该处的情况下改变行为的位置；是模块接口所在的位置。接缝放在哪里本身就是独立的设计决策，与接口背后放什么无关。避免使用：边界（与 DDD 的限界上下文混淆）。

适配器（Adapter）——在接缝处满足接口的具体实现。描述的是角色（它填充什么槽位），而非实质（里面有什么）。

杠杆效应（Leverage）——调用者从深度中获得的好处：每学习一个接口单位获得更多能力。一份实现在 N 个调用点和 M 个测试中产生回报。

局部性（Locality）——维护者从深度中获得的好处：变更、缺陷、知识和验证集中在一处，而不是散布在各个调用者中。一次修复，到处修复。

深度 vs 浅层
深度模块 = 小型接口 + 大量实现：


┌─────────────────────┐
│    小型接口          │  ← 少量方法，简单参数
├─────────────────────┤
│                     │
│   深度实现           │  ← 复杂逻辑被隐藏
│                     │
└─────────────────────┘
浅层模块 = 大型接口 + 少量实现（避免）：


┌─────────────────────────────────┐
│         大型接口                 │  ← 大量方法，复杂参数
├─────────────────────────────────┤
│  薄实现                         │  ← 仅透传
└─────────────────────────────────┘
设计接口时，请自问：

能否减少方法数量？
能否简化参数？
能否将更多复杂性隐藏在内部？
原则
深度是接口的属性，而非实现的属性。 一个深度模块内部可以由小的、可 mock 的、可替换的部件组成——它们只是不属于接口的一部分。一个模块可以有内部接缝（对其实现私有的、被自身测试使用的）以及接口处的外部接缝。
删除测试。 想象删除该模块。如果复杂性消失了，那它只是一个透传层。如果复杂性重新出现在 N 个调用者中，那它物有所值。
接口即测试面。 调用者和测试穿过同一接缝。如果你想测试绕过接口，那模块的形状可能有问题。
一个适配器意味着假设性接缝。两个适配器意味着真实接缝。 除非有东西确实在接缝处变化，否则不要引入接缝。
可测试性设计
好的接口让测试变得自然：

接受依赖，不要创建依赖。


// 可测试
function processOrder(order, paymentGateway) {}

// 难以测试
function processOrder(order) {
  const gateway = new StripeGateway();
}
返回结果，不要产生副作用。


// 可测试
function calculateDiscount(cart): Discount {}

// 难以测试
function applyDiscount(cart): void {
  cart.total -= discount;
}
小表面积。 方法越少 = 所需测试越少。参数越少 = 测试设置越简单。

关系
一个模块有且只有一个接口（它向调用者和测试呈现的表面）。
深度是模块的一个属性，以其接口来衡量。
接缝是模块的接口所在之处。
适配器位于接缝处，并满足接口。
深度为调用者产生杠杆效应，为维护者产生局部性。
被否定的框架
深度作为实现行数与接口行数之比（Ousterhout）：鼓励填充实现。我们改用深度即杠杆效应。
将"接口"视为 TypeScript 的 interface 关键字或类的公共方法：过于狭窄——这里的接口包括调用者需要知道的每一个事实。
"边界（boundary）"：与 DDD 的限界上下文混淆。请说接缝（seam）或接口（interface）。
