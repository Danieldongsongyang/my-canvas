# 深化

如何在考虑依赖关系的前提下，安全地深化一组浅模块。本文假设使用 [SKILL.md](SKILL.md) 中的词汇：**module**、**interface**、**seam**、**adapter**。

## 依赖类别

在评估一个“深化候选模块”时，需要先对它的依赖进行分类。依赖类别决定了深化后的模块应该如何跨越 seam 进行测试。

### 1. 进程内依赖

纯计算、内存状态、无 I/O。

这种情况总是可以深化：把这些模块合并起来，然后直接通过新的 interface 进行测试。不需要 adapter。

### 2. 本地可替代依赖

这类依赖可以在本地测试环境中找到替身，比如用 PGLite 替代 Postgres，用内存文件系统替代真实文件系统。

如果这个本地替身存在，就可以深化。深化后的 module 会在测试套件中配合这个替身一起运行测试。这里的 seam 是内部 seam，不需要在 module 的外部 interface 上暴露 port。

### 3. 远程但自有依赖：Ports & Adapters

这类依赖是你自己的服务，但跨越了网络边界，比如微服务、内部 API。

在 seam 处定义一个 **port**，也就是接口。深模块拥有核心逻辑，而传输层通过 **adapter** 注入进来。测试时使用内存 adapter，生产环境使用 HTTP、gRPC 或队列 adapter。

推荐表述：

“在 seam 处定义一个 port，为生产环境实现 HTTP adapter，为测试环境实现内存 adapter。这样即使系统部署在网络边界两侧，核心逻辑仍然可以位于一个深 module 中。”

### 4. 真正的外部依赖：Mock

这类依赖是你无法控制的第三方服务，比如 Stripe、Twilio 等。

深化后的 module 应该把这个外部依赖作为注入的 port 接收进来。测试时提供 mock adapter。

## Seam 纪律

* **一个 adapter 只说明这是一个假想 seam。两个 adapter 才说明这是一个真实 seam。**
  不要在没有必要时引入 port，除非至少有两个 adapter 是合理的，通常是生产 adapter 加测试 adapter。只有一个 adapter 的 seam 往往只是多余的间接层。

* **区分内部 seam 和外部 seam。**
  一个深 module 可以拥有内部 seam，也就是只属于它实现细节的 seam，主要供它自己的测试使用；同时，它也可以拥有位于自身 interface 处的外部 seam。不要因为测试使用了内部 seam，就把这些内部 seam 暴露到外部 interface 上。

## 测试策略：替换，而不是叠加

* 一旦已经存在针对深化后 module interface 的测试，旧的浅模块单元测试就会变成浪费，应该删除。
* 新测试应该写在深化后 module 的 interface 上。**interface 就是测试表面。**
* 测试应该通过 interface 断言可观察到的结果，而不是断言内部状态。
* 测试应该能够经受住内部重构。它们描述的是行为，而不是实现。如果一个测试在实现变化时也必须跟着改，那它就是越过了 interface，在测试内部实现。
