# 设计两次

当用户想要为某个已经选定的“深化候选模块”探索替代接口时，使用这个并行子代理模式。它基于 Ousterhout 的 “Design It Twice” 思想：你的第一个想法很可能不是最好的。

使用 [SKILL.md](SKILL.md) 中的词汇：**module**、**interface**、**seam**、**adapter**、**leverage**。

## 流程

### 1. 界定问题空间

在启动子代理之前，先为这个选定的候选模块写一段面向用户的解释，说明它的问题空间：

* 任何新接口都必须满足的约束
* 它会依赖哪些依赖项，以及这些依赖项分别属于哪一类，参考 [DEEPENING.md](DEEPENING.md)
* 一个粗略的示意性代码草图，用来让约束变得具体。注意，这不是正式方案，只是为了把约束说清楚

把这些内容展示给用户，然后立刻进入第 2 步。用户可以一边阅读和思考，一边让子代理并行工作。

### 2. 启动子代理

使用 Agent 工具并行启动 3 个以上子代理。每个子代理都必须为这个被深化的模块产出一个**完全不同**的接口设计。

给每个子代理一份单独的技术简报，包括文件路径、耦合细节、来自 [DEEPENING.md](DEEPENING.md) 的依赖类别、以及 seam 背后隐藏的内容。这份简报应该独立于第 1 步中面向用户的问题空间解释。给每个代理分配不同的设计约束：

* 代理 1：最小化接口——目标是最多 1 到 3 个入口点。最大化每个入口点的 leverage。
* 代理 2：最大化灵活性——支持多种使用场景和扩展方式。
* 代理 3：针对最常见的调用方进行优化——让默认场景变得非常简单。
* 代理 4，如适用：围绕 ports & adapters 设计，用来处理跨 seam 的依赖。

在技术简报中同时包含 [SKILL.md](SKILL.md) 词汇和 CONTEXT.md 词汇，这样每个子代理都能用一致的架构语言和项目领域语言来命名概念。

每个子代理需要输出：

1. 接口：类型、方法、参数，以及不变量、调用顺序、错误模式
2. 使用示例：展示调用方如何使用它
3. 实现会在 seam 背后隐藏什么
4. 依赖策略和 adapter，参考 [DEEPENING.md](DEEPENING.md)
5. 取舍分析：哪里 leverage 高，哪里 leverage 薄弱

### 3. 展示并比较

按顺序展示各个设计，让用户可以逐个理解。然后用文字对它们进行比较。比较重点包括：**depth**，也就是接口处的 leverage；**locality**，也就是变化集中在哪里；以及 **seam placement**，也就是 seam 放在哪里。

比较之后，给出你自己的推荐：你认为哪个设计最强，以及为什么。如果不同设计中的某些元素可以很好地组合，也可以提出一个混合方案。要有明确判断——用户想要的是一个有立场的判断，而不是一份菜单。
