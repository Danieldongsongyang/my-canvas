# 转换为 Issues

使用垂直切片，也就是 tracer bullets，把计划拆分成可以独立领取的 issue。

issue 追踪器以及 triage 标签词汇表应该已经提供给你了。如果没有，请运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 收集上下文

从当前对话中已有的上下文开始工作。如果用户传入了一个 issue 引用，例如 issue 编号、URL 或路径，就从 issue 追踪器中获取它，并阅读完整的正文和评论。

### 2. 探索代码库（可选）

如果你还没有探索过代码库，就先探索代码库，以理解当前代码的状态。Issue 的标题和描述应该使用项目领域词汇表中的术语，并遵守相关区域的 ADR。

寻找可以提前重构的机会，让后续实现变得更容易。也就是：“先让修改变容易，再完成这个容易的修改。”

### 3. 起草垂直切片

把计划拆分成 **tracer bullet** 类型的 issue。每个 issue 都应该是一个很薄的垂直切片，端到端贯穿所有集成层，而不是只针对某一层的水平切片。

<vertical-slice-rules>

* 每个切片都交付一条狭窄但完整的路径，贯穿所有层，包括 schema、API、UI、测试。
* 一个完成的切片本身应该可以被演示或验证。
* 任何提前重构都应该先完成。

</vertical-slice-rules>

### 4. 询问用户

把拟定的拆分方案用编号列表展示出来。对于每个切片，展示：

* **标题**：简短的描述性名称
* **被什么阻塞**：哪些其他切片必须先完成，如果有的话
* **覆盖的用户故事**：这个切片对应哪些用户故事，如果源材料中有用户故事的话

询问用户：

* 这个粒度是否合适？是太粗还是太细？
* 依赖关系是否正确？
* 是否有某些切片应该合并，或者进一步拆分？

持续迭代，直到用户批准这个拆分方案。

### 5. 发布 issues 到 issue 追踪器

对于每个已经批准的切片，在 issue 追踪器中发布一个新的 issue。使用下面的 issue 正文模板。因为这些 issue 会被视为已经准备好交给 AFK agents 处理，所以除非另有说明，否则发布时要带上正确的 triage 标签。

按照依赖顺序发布 issues，也就是先发布阻塞其他工作的 issue，这样后续 issue 就可以在 “Blocked by” 字段里引用真实的 issue 标识符。

<issue-template>
## 父级

引用 issue 追踪器中的父 issue。如果源材料本身就是一个已有 issue，则填写；否则省略这一节。

## 要构建什么

简洁描述这个垂直切片。描述端到端行为，而不是逐层描述实现。

避免写具体文件路径或代码片段，因为它们很快会过时。例外情况是：如果某个原型产出的代码片段比文字更准确地表达了某个决策，例如状态机、reducer、schema、类型形状，那么可以把它内联到这里，并简要说明它来自原型。只保留能体现关键决策的部分，不要放完整可运行 demo，只放重要片段。

## 验收标准

* [ ] 标准 1
* [ ] 标准 2
* [ ] 标准 3

## 被什么阻塞

* 引用阻塞当前工作的 ticket，如果有的话

如果没有阻塞项，则写：“None - can start immediately”。

</issue-template>

不要关闭或修改任何父 issue。
