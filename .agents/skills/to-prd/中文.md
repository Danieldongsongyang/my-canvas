这个 skill 会基于当前对话上下文和对代码库的理解，生成一份 PRD。不要采访用户——只需要综合你已经知道的信息。

issue 追踪器以及 triage 标签词汇表应该已经提供给你了。如果没有，请运行 `/setup-matt-pocock-skills`。

## 流程

1. 如果你还没有探索过代码库，就先探索 repo，理解当前代码库的状态。在整份 PRD 中使用项目领域词汇表中的术语，并遵守相关区域的 ADR。

2. 规划你准备在哪些 seam 上测试这个功能。优先使用已有 seam，而不是创建新的 seam。尽可能使用最高层级的 seam。如果需要新的 seam，也要尽可能在最高层级提出。代码库中的 seam 越少越好——理想情况下只有一个。

向用户确认这些 seam 是否符合他们的预期。

3. 使用下面的模板编写 PRD，然后发布到项目 issue 追踪器。应用 `ready-for-agent` triage 标签——不需要额外的 triage。

<prd-template>

## 问题陈述

从用户视角描述用户正在面对的问题。

## 解决方案

从用户视角描述这个问题的解决方案。

## 用户故事

一份很长的、编号排列的用户故事列表。每个用户故事都应该使用以下格式：

1. 作为一名 <角色>，我想要 <功能>，以便 <收益>

<user-story-example>
1. 作为一名手机银行客户，我想查看我的账户余额，以便我能更明智地决定自己的消费。
</user-story-example>

这份用户故事列表应该非常全面，覆盖该功能的所有方面。

## 实现决策

列出已经做出的实现决策。可以包括：

* 将要构建或修改的模块
* 这些模块中将要修改的接口
* 来自开发者的技术澄清
* 架构决策
* Schema 变更
* API 契约
* 具体交互

不要包含具体文件路径或代码片段。它们很可能会很快过时。

例外情况：如果某个原型产出的代码片段比文字更准确地表达了某个决策，例如状态机、reducer、schema、类型形状，那么可以把它内联到相关决策中，并简要说明它来自原型。只保留能体现关键决策的部分，不要放完整可运行 demo，只放重要片段。

## 测试决策

列出已经做出的测试决策。包括：

* 描述什么样的测试是好测试，也就是只测试外部行为，而不是实现细节
* 将要测试哪些模块
* 测试方面的先例，也就是代码库中类似类型的测试

## 不在范围内

描述这份 PRD 不覆盖的内容。

## 进一步说明

关于该功能的其他补充说明。

</prd-template>
